
[ web4 ]

1. 프로젝트 개요
    목적:  web3에서 학습한 기초적인 CRUD(Create, Read, Update, Delete) 패턴 복습,
        예외 처리 아키텍처, 엔티티 매핑 심화 기술(JPA Auditing, 복합키 설정),
        IP 기반의 추천 중복 방지 비즈니스 로직을 구현하여 프로그래밍 완성도 향상.

    개발 환경 및 구조:
        Backend     :  Java 21, Spring Boot, Spring Data JPA
        Frontend    :  Thymeleaf HTML Template Engine
        Architecture:  MVC 패턴 및 계층형 아키텍처 (Controller ➔ Service ➔ Repository ➔ DB)

2. 주요 실습 내용
    ① 방명록(Guestbook) 기본 CRUD 및 예외 처리
        뷰 폴더:  templates/ 및 templates/error/
        실습 파일:  GuestbookController.java, GuestbookService.java, GuestbookRepository.java,
            GuestbookExceptionHandler.java, list.html, writeForm.html, updateForm.html, error.html
        내용:  기존의 반복적인 try-catch 방식의 예외 처리에서 벗어나,
            Spring이 제공하는 @ControllerAdvice와 @ExceptionHandler를 활용한 중앙 집중식 전역 예외 처리 메커니즘을 구축.
            클라이언트 단에서는 Spring Boot의 에러 페이지 매핑 전략을 이해하고
            상태 코드별(404.html) 및 Fallback 에러 페이지(error.html)를 구현.

    ② IP 기반 방명록 추천 중복 불가 기능 (심화 매핑)
        뷰 폴더:  templates/
        실습 파일:  GuestbookRecommendEntity.java, GuestbookRecommendKey.java (Embeddable),
            GuestbookRecommendRepository.java, GuestbookService.java
        내용:  기본 CRUD 처리를 기반으로,
            요청 클라이언트의 IP 주소를 추출하여 '방명록 글 번호'와 '유저 IP'를 조합한 복합키(Composite Key) 구조를 설계.
            @Embeddable 및 @EmbeddedId 어노테이션을 활용해 데이터베이스 복합키를 JPA 엔티티로 완벽하게 매핑하고,
            동일 IP에서 특정 글에 대한 추천 중복을 원천 차단하는 비즈니스 로직을 실습.


3. 핵심 동작 흐름 (Flow)
    ① 방명록 등록/수정 시 데이터 변환 및 시간 자동화 흐름
        [Client] writeForm.html 제출
           ➔ [Controller] GuestbookDTO로 요청 데이터 수신
           ➔ [JPA Auditing] AuditingEntityListener 작동 (생성/수정 시간 자동 세팅)
           ➔ [Repository / DB] 최종 DB 반영 (INSERT / UPDATE)
    ② 전역 예외 처리 (Global Exception Handling) 아키텍처 흐름
        [Service Layer] 비즈니스 로직 검증 실패 (예: PasswordException 발생/Throw)
           ➔ [Spring MVC] 에러 포착 후 전역 예외 핸들러 검색
           ➔ [GuestbookExceptionHandler] @ExceptionHandler(PasswordException.class) 메서드 매핑 및 실행
           ➔ [Redirect] RedirectAttributes(addFlashAttribute)를 통해 안전하게 에러 메시지(msg) 전달
           ➔ [Client] 사용자에게 명확한 에러 안내 및 리다이렉트 페이지 노출

4. 실습 포인트
    a. web4는 방명록을 주제로하여 web3 의 CRUD의 기본기를 연습
    b. 예외를 처리하는 흐름 이해 (기본 try-catch, Exception Handler, view error 페이지)
    c. IP 기반 추천 중복 불가 기능 (IP주소 추출, Embedded Entity 사용-복합키)
        - 기본기 다지기:  web4는 방명록 애플리케이션을 주제로 하여
            web3에서 배운 데이터 추가, 조회, 수정, 삭제(CRUD)의 기본기를 확실하게 연습.
        - 에러 핸들링:  컨트롤러 메서드마다 try-catch로 작성했던 코드를 정돈하고,
            예외 처리 흐름(Service Throw → Exception Handler → View Error Page)의 유기적인 관계 이해.
        - 네트워크 정보 활용 및 복합키 설계:  클라이언트의 IP 주소를 추출하는 방식을 배우고,
            JPA에서 단일 기본키가 아닌 두 개 이상의 컬럼을 조합해 유일성을 보장하는 Embedded Entity(복합키) 구조를 설계 및 구현.


** 알아두기 **
📌 엔티티 식별자 생성 전략:  @GeneratedValue
    - JPA에서 엔티티의 기본키(Primary Key)를 자동으로 생성할 때 사용하며, 데이터베이스에 따라 최적의 전략을 선택해야 함.
    - GenerationType.IDENTITY: 기본키 생성을 데이터베이스에 위임. MySQL - AutoIncrement과 함께 사용.
    GenerationType.AUTO (기본값): 선택한 JPA 구현체(Hibernate)가 데이터베이스 방언(Dialect)에 맞춰 자동으로 생성 방식을 결정.

📌 데이터 생성/수정 시간 자동화:  JPA Auditing
    - 데이터의 생성일시와 수정일시는 데이터 관리 및 추적에 필수적.
    - 이를 개발자가 매번 코드로 직접 넣지 않고 엔티티의 생명주기를 감지해 자동으로 기록해 주는 기능.

    적용 방법:
        엔티티 클래스 상단에 @EntityListeners(AuditingEntityListener.class)를 선언하여 JPA의 이벤트 리스너를 활성화.
    주요 어노테이션:
        @CreatedDate:  엔티티가 최초로 저장(Persist)될 때 현재 시간이 자동으로 저장.
        @LastModifiedDate:  엔티티의 값이 변경(Update)될 때마다 변경 시간이 자동으로 갱신.
        @CreatedBy / @LastModifiedBy:  등록자, 수정자를 자동으로 기록하고 싶을 때 사용. (Spring Security 등과 연동 필요)

📌 JPA 복합키:  @Embeddable
    - 데이터베이스 테이블 설계 시, 단일 컬럼이 아닌 두 개 이상의 컬럼을 묶어서
        하나의 복합 기본키(Composite PK)로 지정해야 할 때가 있음.
        JPA에서는 이를 객체지향적으로 표현하기 위해 별도의 키 클래스를 생성하고 상단에 @Embeddable을 선언.
    - 이번 실습에서는 글 번호(GuestbookEntity)와 추천인 IP를 묶어 중복 추천을 막는 GuestbookRecommendKey를 설계할 때 사용.

📌 리다이렉트 데이터 전달 방식 비교: RedirectAttributes
    - PRG(Post-Redirect-Get) 패턴 구현 시, 화면을 전환(Redirect)하면 이전 Request와 Model에 담긴 데이터는 소멸.
      이때 리다이렉트된 페이지까지 안전하게 데이터를 전달하기 위해 RedirectAttributes 객체를 사용.

      메서드                   전달 방식             데이터 유지 시간       URL 노출 여부           내부 동작 원리 및 특징
      ----------------------------------------------------------------------------------------------------------------------------------
      addAttribute()          쿼리 파라미터          다음 요청까지 지속     URL에 그대로 노출됨      String으로 변환 가능한 데이터만 전달 가능하며,
                              (Query Parameter)                        (예: ?msg=success)     새로고침을 해도 URL에 파라미터가 유지됨.
      addFlashAttribute()     FlashMap             단 한 번만 사용       노출되지 않음            내부적으로 Spring이 HttpSession을 생성하여
                                                   후 소멸URL에                                데이터를 잠시 보관.
                                                                                              DispatcherServlet이 리다이렉트 후 세션에서
                                                                                              데이터를 꺼내 Model로 자동으로 복사해 주며,
                                                                                              복사 직후 세션에서 데이터가 자동 삭제되어
                                                                                              일회성 메시지(경고창, 성공 메시지) 전달에 최적화.
      ----------------------------------------------------------------------------------------------------------------------------------

📌 데이터 정렬의 유틸리티:  Spring Data JPA Sort 객체
    - SQL 데이터베이스의 ORDER BY 문을 소스코드 레벨에서 유연하고 안전하게 작성할 수 있도록 돕는 유틸리티 클래스.
      문자열로 하드코딩하는 SQL 문과 달리, 자바 객체로 다루기 때문에 IDE의 자동완성과 컴파일 시점의 타입 체크 이점을 얻을 수 있음.
    - Sort.Order: "어떤 필드를 기준으로, 어떤 방향(오름/내림차순)으로 정렬할 것인가"에 대한 하나의 단위를 정의하는 객체.

    주요 구성 요소:
        property    : 정렬 기준이 되는 엔티티의 멤버 변수명(컬럼명)
        direction   : 정렬 방향 (Sort.Direction.ASC / Sort.Direction.DESC)
        ignoreCase  : 영문자 정렬 시 대소문자 무시 여부 설정

📌 데이터 안전성을 위한 집합:  enum (열거형)
    - 상수들의 집합을 정의할 때 사용하는 특수한 자바 클래스.

    도입 배경:  등급 정보를 단순 문자열(String grade = "HIGH";)로 관리하면 오타가 나거나
        잘못된 값(예: "HIGGGH")이 들어오는 것을 컴파일 시점에 막을 수 없음.
        상수 값을 안전하게 타입으로 제한하기 위해 enum을 사용.
    특징:
        암묵적으로 public static final 구조.
        일반 클래스처럼 멤버 변수, 생성자, 메서드를 가질 수 있어
        상수에 비즈니스적 속성을 부여해 고도화할 수 있음.

📌 Spring Boot의 영리한 Fallback:  View Error 처리 우선순위
    - 예외 핸들러가 잡아내지 못했거나 웹 서버 자체에서 발생한 에러(예: 없는 주소 접근 404)에 대해
      사용자가 톰캣의 삭막한 기본 에러 화면을 보지 않도록 Spring Boot는 정해진 관례 규칙에 따라 예외 페이지를 탐색.

    자동 탐색 및 매핑 순서:
        1. 가장 먼저 /error 라는 매핑 규칙을 가진 커스텀 컨트롤러가 있는지 확인.
        2. 없다면 src/main/resources/templates/error/ 폴더 내부에서 발생한
           HTTP 상태 코드와 매칭되는 파일(예: 404.html, 500.html)을 찾아 브라우저에 반환.
        3. 구체적인 상태 코드 파일이 없다면 해당 폴더 내의 error.html (Fallback, 기본 에러 페이지)을 찾아 최종적으로 매핑.
        * 따라서 개발자는 templates/error/ 패키지 구조 안에 규칙에 맞는 이름으로
          HTML 파일만 만들어두면 별도의 컨트롤러 코딩 없이 깔끔한 에러 화면을 구현 가능.
